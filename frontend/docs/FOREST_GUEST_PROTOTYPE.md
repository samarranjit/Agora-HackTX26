# Storywood guest adventure

**Current mode selection:** the guest adventure below remains offline with unchanged gameplay rules. The landing also offers an explicitly selected authenticated account mode when `VITE_API_BASE_URL` is configured. Account PDF processing now uses the verified `origin/main` study-pack contract. Older references below to an unmapped anonymous upload are historical; that seam has been replaced. See [BACKEND_MODE.md](BACKEND_MODE.md) for current account behavior and API limits.

The active frontend remains root `src/`, started with `npm.cmd run dev`. `frontend/ui/` is untouched. The default route opens a PDF landing dialog over an uphill forest, with five fairy-tale collectibles, two trail encounters, a drawbridge and an immense dragon throne hall. Existing Three.js player controls, modal focus, instanced scenery, scene cleanup and the backend client/tester are reused. No dependencies were added. Earlier design/implementation documents describe the original plan; this guide records the current scoped guest prototype.

## Play

1. Select/drop a PDF, or explicitly choose **Explore the guest demo without a PDF**. With no configured upload endpoint, **Continue with this PDF locally** keeps the file in memory and starts placeholder gameplay without sending it. WASD moves, mouse/pointer lock or drag looks, Space jumps, Shift sprints, E interacts and Escape pauses. Lanterns and branching stepping stones lead toward the items; the pause-menu journal gives this run's east/west hints.
2. Find King Triton's Trident by the pond, Red Riding Hood's Cloak in the woods, Cinderella's Glass Slipper at a stone arch, Humpty Dumpty's Eggs under a shelter, and Alice's Potion among violet mushrooms. Locations vary each run.
3. Each item has exactly three questions, shown one at a time. Their prompt is `*filler question*`; choose `answer`, `placeholder option B`, or `placeholder option C` and submit. The accepted value remains `answer`; the two distinct placeholder alternatives exercise incorrect-answer feedback. These are explicitly offline choices, not PDF-generated content. **Learn more** reveals `filler explanation` for collectibles only. Content is centralized in `src/game/forestContent.js` (15 distinct collectible questions).
4. Complete all three correctly to collect an item, award **20 prototype XP once**, and record its checkpoint. Answers before the third question award no XP. Closing or switching challenges preserves partial answers, feedback and remaining health.
5. Collect **all five items**, reaching **100 XP**, to lower the bridge and raise the portcullis. Collision remains closed until the animation is finished. Walk through the entrance to record the castle checkpoint and enter the hall.
6. Along the route, the Goblin becomes eligible after two completed collectibles. The Big Bad Wolf appears farther uphill after the Goblin is defeated. Approaching either starts an introduction once per run. Each starter-tier encounter needs one correct placeholder answer, awards no XP, and shares the three-heart limit. Closing it preserves progress; use E nearby or the pause menu to resume. An unfinished combat challenge prevents switching to another target. Neither encounter offers help.
7. Follow the long carpet through the hall, approach the Storykeeper Dragon and press E. Its local final encounter reuses three studied placeholder questions, offers no help and awards no extra collectible XP. Three correct answers complete the prototype adventure. The princess is separately visible behind/right of the dragon on the raised throne area and can be approached for a dialogue. The arch behind you returns to the forest. There is no separate rescue progression or server victory.

The clarified health rule is **one of three displayed hearts lost per incorrect answer**, equivalent to one-third of total health. Three mistakes exhaust health. A wrong answer never advances the question. The third mistake immediately replaces the entire run: new run ID, start position, three hearts, zero XP, no items/challenge history/checkpoints and a locked castle. Previous run events cannot apply to the new run. No heart recovery occurs on dialog close, pause, collection or castle entry.

Only Medium is offered internally, without a selection step. The requested five-item **20 × 5 = 100 XP** forest progression is a scoped prototype rule. Earlier Easy/Medium/Hard settings and the earlier 5-XP relic constant remain unchanged for the preserved implementation; backend rules are not modified.

## Pointer lock and multiple-choice presentation

Gameplay activation now requests pointer lock on the current canvas through the shared controller. Forest question completion/close, encounter introduction close, journal/gate/princess close and menu resume all use the same intentional resume callback. The preserved indoor/courtyard close paths also resume through the controller. Activating a newly mounted room requests lock once, including sample loading and hall/forest transitions. Modal opening clears input and releases lock before interaction; resuming preserves position and camera orientation.

The controller deduplicates requests while one is pending or the canvas is already locked, listens for promise rejection and legacy `pointerlockerror`, and releases late acquisitions if a modal opened or the canvas was disposed. A newly constructed room defers its one initial attempt to a microtask so React's development setup/cleanup cycle cannot acquire lock on a discarded canvas; explicit resumes still request synchronously in the gesture. Browser Escape/blur/hidden-page unlocks pause gameplay without a reacquisition loop. If browser policy declines a resume request, the player can click the canvas or **Resume mouse look** for one recovery attempt, with drag-look retained. There is no dedicated mouse-unlock control. Reacquisition still depends on browser policy and a permitted gesture.

`MultipleChoiceAnswer.jsx` displays explicit `{ id, label, value }` choices using required native radio inputs, a visible selected state, an explicit submit button, disabled submitted state and a synchronous duplicate-submit latch. The caller supplies choices and owns evaluation. Each turn remounts the form; forest feedback stores the submitted value so a closed/reopened question can show its submitted selection. The existing reducer still owns health, rewards, completion, reset and stale-event guards. Wrong options do not advance; retry remains explicit. Combat help remains blocked in both UI and reducer.

The five collectible challenges, Goblin, Wolf and dragon all use the shared placeholder choices, preserving the existing `answer` convention and questions. The preserved indoor quiz uses the same form with its existing ATP/Nucleus/Proteins sample content. No generated backend choices, new response fields or network calls are invented. A future backend adapter must map its agreed option IDs/labels/values explicitly and keep correctness/rewards server-owned. The separate account API question UI and PDF selection/upload code are unchanged by this task.

## Guest lifetime and honest backend boundary

The default adventure is **explicitly offline**. Run state is held only in React memory, with no localStorage/sessionStorage save, token, account creation or gameplay requests. The optional PDF submission described below is separate and requires explicit configuration and user submission. Reload or a new visit starts from zero and clears the selected PDF/receipt. A back/forward-cache revisit also resets them. Switching tabs merely pauses. A full gameplay reset replaces local run state and layout; a selected PDF remains available during the same visit. No server run exists to reset, and local reset does not delete a configured endpoint's uploaded files.

Existing account sessions in browser storage are neither loaded into nor modified by this guest route. No account is created behind the scenes, and local XP is labeled **prototype XP**, never server-authoritative XP.

The existing backend requires registration/login and bearer tokens. Inspection of `origin/main` routes/schemas/authentication confirms no genuine guest-session, collectible-group or run-reset endpoint. Backend source remains absent from this checkout; no branch was merged or switched to obtain it. The default server selects Forest Goblin before Troll and Dragon and uses different health/reward rules. Therefore the hall encounter is not represented as a server dragon battle.

**Backend API Tester** remains development-only in the start/pause menu. It uses the existing real client and account endpoints, in an isolated developer session; its account UI never appears in the production guest flow. Tester mutations affect its explicit account, not the local forest run. It creates no requests merely by opening. Legacy courtyard/API integration and the indoor room remain available in development at `/?demo=courtyard` and `/?demo=indoor`.

## Smallest backend handoff still needed (proposed, not implemented)

The backend teammate must agree on these capabilities before connecting this guest adventure. No calls to the following proposed endpoints have been invented in the frontend:

- **Create temporary guest:** for example `POST /api/guest-sessions`, issuing an opaque bearer token, server-owned guest/run IDs, expiry and a Medium campaign configuration. Make creation retry-safe with one idempotency key per intended visit. Do not use the AI module's `sessionId` as authentication or create hidden permanent accounts.
- **Reset current guest run:** a guest-only operation, for example `POST /api/me/run/reset`, atomically replacing run identity, XP, health, collectible completions, checkpoints, pending attempts and gate/dragon flags. Fence stale answers by run identity; preserve safe idempotent retries. This must not reset a permanent account accidentally.
- **End/expire guest:** an explicit end operation plus mandatory server TTL cleanup. Suggested prototype policy: a 60-minute absolute guest lifetime, revoke access at expiry, then a periodic sweep at least every 15 minutes that removes guest-owned records, uploaded PDF bytes, question sets/answers and provider indexes. A page-close request is best-effort only; server expiry must work if a browser disappears. These times are proposed policy values requiring teammate agreement, not existing behavior. Ordinary account logout currently revokes a token without deleting account data.
- **Authoritative collectible challenges:** initialize exactly five stable items with three public questions each. The existing answer endpoint can be extended with stored collectible context, but the server must track accepted questions, award 20 XP once only after all three are correct, record checkpoints, and require all five plus 100 XP to unlock. Never accept client-supplied XP or a completion flag as evidence.
- **Health/reset and dragon campaign:** apply the agreed three-mistake rule and full guest reset on zero; expose the result to the frontend. Configure a guest campaign with the dragon as its actual final opponent, rather than relabeling a Forest Goblin response. Auth alone does not supply these gameplay rules: existing engine/backend policies need a scoped campaign/rule extension and tests.

Regenerate OpenAPI and update the shared client's validators/tests with that agreed contract. Keep token ownership, uploaded-file ownership and private answer keys on the server. The PDF endpoint is blank by default; configuring it does not establish a server cleanup policy or genuine guest authentication.

## Seeded world and collision

`createForestRun` creates one immutable layout using its run UUID as the seed. `generateForestLayout(seed)` in `src/forestLayout.js` is deterministic: five separated uphill bands vary the items' side and coordinates, tree clusters/heights, rocks, shrubs and gentle off-path terrain. The start, castle, main route and bridge remain fixed. Main-path corridors, horizontal branches, item clearings and enemy clearings are reserved before scenery placement. Placement attempts are bounded. React owns the layout; rendering, terrain height, interactions, checkpoints and collision all consume it. Answers, menus and ordinary rerenders never reshuffle it.

The Goblin and Wolf occupy separated randomized route bands, at least 16 world units apart, with eligibility enforced by the reducer. Two completed collectibles define the introductory milestones; the prototype's easier tier means one question rather than three, not a claim about generated educational difficulty. Combat explanations are rejected in the reducer as well as hidden in the UI, including for the dragon.

Pedestal base collision uses a 1.08-unit radius including player clearance and substeps for normal/diagonal approaches. Checkpoints are placed safely 1.8 units toward the main path rather than inside the solid pedestal. Interaction ranges remain reachable. The hall is 80 by 152 units, with a 48-unit ceiling, 34-unit columns, a 117-unit approach to the dragon and a walkable ramp to the raised court. Column bases, walls and characters block traversal.

## PDF landing and upload boundary

`src/PdfLanding.jsx` owns selection/validation/submission presentation; `ForestJourney.jsx` owns the selected `File` and receipt in memory. Click-to-select, drop, filename/size, removal, reselection, busy/error states and local continuation are available. Validation requires a nonempty `.pdf`, a compatible/empty MIME type, a `%PDF-` header in the first 1024 bytes and the size limit. This is a lightweight check, not PDF parsing or a substitute for backend validation. Selection never uploads automatically. No file bytes are logged or stored in browser storage.

See `BACKEND_INTEGRATION.md` for configuration and the exact multipart request/response seam. In brief, `VITE_PDF_UPLOAD_ENDPOINT` must be explicitly set; `VITE_PDF_MAX_MB` defaults to 20. `src/api/profilePdf.js` exports `uploadProfilePdf(file)` using the shared API transport, a multipart field named `file`, no account bearer token and no automatic retry. `interpretProfilePdfReceipt` is the exact place to map the teammate's eventual response. An HTTP receipt is labeled as submission only: parsing and generated questions remain unmapped. Successful upload does not replace placeholder questions. The separate authenticated Study Materials flow and developer tester retain their existing contract.
